- No integration tests - my preferred type of test (high value and less vulnerable to false positives as the codebase evolves), but left out due to lack of time.
- Did not implement pagination, but would be worth doing for a list UI like this.
- There is a considerable amount of duplicated code for fetching from postgres, implemented in both the service and the app. Rather than wrestle with docker and ts config I've chosen to just copy and paste
- UI edge cases are not covered e.g. accidentally creating risks then wanting to dismiss that part of the UI
- Chose to write to the audit table as part of the transaction, rather than afterwards. More robust, but also means if there's an issue with the audit table then it's also impossible to write to the other tables (the core product), which might not be
- The uniqueness constraint on model_risks on category + context + mdel_id was added quite late in the process and I've not thought about the consequences for error handling.
- The LOW | MODERATE | HIGH enum should idelaly be a single shared implementation, but is not as DRY as I would like.
- Have made owner on models optional in the schema purely to avoid having to implement an owner selection UI. It shoudl probably be a required field with a DB look up to choose from an org's existing owners/add a new one.
- When adding a model the ideal (faster UX and less db querying) would be to return the full model data and then to append that to the model table client side. But for this exercise I'm just redirecting to and reloading the models table as it is far simpler. Similarly, error handling of the api response when creating a model is virtually non-existent due to time constraints.
- The audit log - just creating a single entry for create, though arguably this should be a create followed by multiple update logs for each relationship added. The audit_log table woudl need to be a richer model in order to do this, so leaving out for now.
- The scoping to the current org does not feel particularly robust. RLS would fix any security/privacy concerns, but it's still good practice to explicitly add teh org_id in your WHERE clauses, and there is nothing to enforce that. It'd be good to have a utility wrapping db query which does this by default. Or maybe some very strict guidance in claude.md woudl help here.
- Because the UI does some server side calling to the db directly, and some via /api there's a mishmash of auth stubbing vs hard-coding of values. I prefer server-rendering for initial page load - often better page speed and UX - which is why not everything goes through the api layer. In a production app both routes would likely share an oauth JWT (cookie for SSR, header for api calls) and therefore share code for auth, but in this POC they are totally separate.
- Normally I spend more time telling claude to simplify things/YAGNI. Due to time constraints and getting close to session token limit, I mostly let things like handling unnecessary edge cases in scripts/tests go by. Normally I would tell clause they're not needed and potentially turn this into a rule added to claude.md
- In some places the error handling is blunt - in prod apps I would typically inspect the error to check for 4xx vs 5xx and modify the user response and control flow accordingly (e.g. might retry a 5xx)
- The risk aggregate score API is not actually used anywhere. The project brief did not state how it should be used. I did intend to bring it into the table view but, because I'd used server side rendering, there wasn't an obvious need for the /api endpoint (I could've just called the API server side as part of the page render). My plan was to call it on the client side to lazily populate the aggregate score column but ran out of time. To be honest, I don't think that would've been a very good user experience and it'd be better to just call the scoring service on the server side, but this would add many api calls in the crtical path so is not ideal. It needs more thought to figure out the best approach to rendering the aggregate risk scores quickly and reliably.
